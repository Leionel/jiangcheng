## 0. 一句话结论

P0 的「拍照 → 出卡 → 三回合战斗 → 结算 → 图鉴」闭环真实可跑，工程完成度高于同阶段常见 Demo。
但**可玩性仍然是一次性的**：战斗没有 AI 参与、没有局内取舍、三回合几乎必然靠 HP 百分比判定，玩家第二次进入时没有任何新目标或新信息。P1 的高收益改动不在"加功能"，而在三处：**让 AI 真正支配敌方出招、给被克对局一个可玩的翻盘手段、把每局结果沉淀成可比较的战绩**。

## 2. 六个必答问题

### 2.1 当前已经实现哪些完整玩法？哪些只是演示或占位？

**完整可用（代码 + 运行双重验证）**

1. **捕获 → 出卡**：5 个内置样本、拍照/上传/拖拽；图片格式/大小/尺寸校验；64×64 像素统计（主色、明暗、构图）→ 本地草稿；有 Key 时把最长边 1100px、JPEG 0.82 的压缩图发给模型做视觉摘要与设定；`live_ai / demo / fallback` 三态在卡面、页头、日志里一致标注。相关代码：`src/App.tsx`、`src/features/monsters/analyze.ts`、`src/shared/ai/client.ts`、`server/server.mjs`。
2. **规则化出卡**：属性、HP/ATK/DEF/SPD、两个技能、造型配方由 `build.ts` / `skills.ts` / `elements.ts` 的哈希+规则函数决定；同图同 variant 可复现；AI 草稿不能改数值（`docs/HANDOFF.md` §4 不变量 1）。三处 zod 校验（服务端请求、响应、`coerceDraft`）都在。
3. **战斗**：`battle.ts` 是纯函数；天气由 seed 决定并公示；先手按「优先级 → 速度 → 种子」；6 技能效果（伤害/防御/回血/佯攻/抢先）全部实现；HP 不为负；最迟 3 回合结算；同种子同出招必得同结果；敌方意图在出招前**准确预告**（`chooseIntent` 只依赖可见状态）。
4. **卡面/选敌**：属性克制关系、技能详情、4 个对手与克制提示；默认选中对我方最有利的对手（`CardView.tsx`）。
5. **结算**：胜/负/平、剩余 HP、总伤害、关键行动、伤害公式依据、可复现种子展示（`ResultView.tsx`）。
6. **图鉴**：localStorage 持久化（上限 24）、双列数值对比、切换出战、删除、空卡位（`store.ts` / `GalleryView.tsx`）。
7. **分享**：Canvas 720×1040 导出精灵卡 PNG，不含原图与位置（`share.ts`）。
8. **失败兜底**：无 Key / 断网 / 超时 / schema 不过 → 演示或降级模式，全流程可走完，并如实标注。

### 2.2 第一次游玩 vs 第二次游玩的动力分别是什么？

**第一次（0–60 秒）动力成立且顺畅。**
- 0 秒可点「热干面」大卡；无 Key 时 ≤3 秒出卡；有 Key 时约 4 秒（样本）/ 8 秒（真图）。
- "我的照片/样本变成一只会打架的精灵"是明确的新奇点；卡面证据标签把图片与角色连起来。
- 默认对手按克制排序，第一场胜率高（样本多数 79–100%），正反馈及时。
- 实测 E2E：从首页点击到进入战斗 < 10 秒。

**第二次及以后，动力明显不足。**
- 没有战绩、没有解锁、没有连胜/连败、没有收藏目标；胜负只影响一屏结算文案。
- 再次捕获只改变属性/数值/技能组合，但**战术选择空间不变**（永远 2 个技能、3 回合、同样的意图预告），打法重复。
- 图鉴上限 24 且无锁定，玩家不会为"收藏"投入；空卡位只是装饰。
- 分享卡是唯一可带走的产物，但它不记录本局结果。
- 内置样本在有 AI 时每次都被重新生成（点击样本 → 文本调用模型 → 名字/设定变化），"5 个固定样本"的展示意义被削弱，第二次点同一个样本也不会得到可预期的结果。

### 2.3 AI 实际参与哪些决策？哪些只是固定规则/模板？

| 环节 | 谁在做 | 说明 |
|---|---|---|
| 读图（类别/特征/颜色/置信度） | **实时 AI**（上传且开启实时时）或本地像素规则 | `server.mjs` SYSTEM_PROMPT + `VisionSchema` |
| 名字 / 主题文案 / 造型配方 | **实时 AI**（受枚举白名单限制）或本地命名器 | `build.ts:181-209` |
| 属性（Element） | **实时 AI 草稿**决定（`resolveElement`），失败时才按分类映射 | `build.ts:123-126` |
| 第二技能偏好 | **实时 AI 草稿**决定，第一技能强制 BURST | `skills.ts:99-122` |
| HP/ATK/DEF/SPD | 规则哈希，AI 不可改 | `build.ts:57-84` |
| 伤害、胜负、天气、先手 | 规则引擎 | `battle.ts` |
| **敌方出招** | **100% 固定规则**（`chooseIntent`），AI 不参与 | `battle.ts:90-149` |
| **战况播报/敌方心理** | 模板字符串 | `battle.ts` 日志、`enemies.ts` taunt 静态文本 |

**结论**：AI 目前是"出卡内容生成器 + 视觉识别器"，它通过属性与第二技能**间接**影响战斗，但战斗过程中 AI 完全缺席。这既不符合本轮 P1 要求"AI 必须实际影响玩法"，也没有兑现规格书 §4.8 的 P1 战况播报。

### 2.4 哪些功能缺乏即时反馈、策略性或可见状态变化？

1. **HP 条已有 0.45s 过渡（`base.css:443`），但缺少低血量警示与扣血强调**：数值变化虽平滑，颜色始终不变，危险状态只能靠旁边的小字「危险」；配合击倒/回合切换的舞台提示缺失，回合节奏仍然偏平。
2. **回合切换没有仪式感**：R1→R2→R3 只有顶部三个小方块变色，没有"第 2 回合"的舞台提示；战报是批量追加，最新一行没有高亮。
3. **KO/终结没有演出**：一方 HP 归零与"三回合比血"使用同一块 `result-banner`，没有击倒印章/定格，高潮被压缩成一句"站不住了"。
4. **意图条不含来源信息**：玩家不知道敌方这一招是"规则算出来的"还是"AI 选的"；P1 接入 AI 后若不标注，就会违反"AI 模式如实标注"的既有原则。
5. **技能预测只给单点伤害**，没有告诉玩家"这一击之后我会不会倒"；例如"预计 31 伤害"但没有"你剩 20 HP，会倒"。决策依据不完整。
6. **战术维度缺失**：两个技能里通常一个是 BURST 固定输出，另一个是防御/回血/先手/佯攻；每回合的最优解基本可以在第一回合算完，缺少"一次性大动作"的取舍。
7. **结算页没有"战绩变化"**：赢了/输了没有任何持久状态变化；"关键行动"只展示最后 6 条，没有高亮翻盘/失误节点。
8. **图鉴对比**：标签错误（克制倍率行）、无战绩、无排序/筛选，卡与卡之间除数值外没有可比较的"使用表现"。

### 2.5 哪些问题会导致游戏重复、无聊或体验中断？

**重复/无聊（核心）**

1. 3 回合、2 技能、意图完全可预测 + 无 AI 变招 → 同一只精灵对同一敌人的最优出招序列几乎是固定的；第二次对局没有新信息。
2. 击倒率低、平均 3.0 回合 → "三回合比血"占主导；玩家在 R2 结束就能算清胜负，R3 只是执行。
3. 被克对局基本必败（0–21%）→ 不是"难"，而是"没有选择"；玩家只能换对手，等于承认这套战斗没有翻盘玩法。
4. 没有战绩/成长/目标 → 第二次打开产品的理由只剩"再拍一张"，而新卡对战斗策略的改变很有限。
5. 样本在实时 AI 下每次被重新生成 → 固定的 5 个样本不能作为"可比较的样例"，削弱了第二次游玩的参照系。

**体验中断风险**

6. 捕获只有 30s 前端超时 + 8s"改用演示策略"出口；README/HANDOFF 说 6 秒，实际代码是 8 秒（`App.tsx:119`），文档与实现不一致。
7. 实时 AI 上传约 8 秒，期间只有显影弹窗；对于没耐心的人，唯一的出口是"跳过"（这会把一张卡降级成演示模式）。
8. 服务端限流 20 次/分钟/IP（`server.mjs:94`），若 P1 每回合调用 AI（3 次/局），连续试玩几局就会 429；且 429 会触发降级，演示时容易被误认为"AI 坏了"。
9. 图鉴写满 24 条后静默淘汰最早一只，玩家会以为"卡丢了"。
10. 无错误边界：任何未捕获的渲染错误都会整页白屏（React 18 默认行为）。
11. `server.mjs` 对畸形 URL 的 `decodeURIComponent` 可能抛错，异步 handler 没有兜底（本地 Demo 风险低，但属于稳定性问题）。
12. 无代码分割：单 JS chunk 264KB（gzip 84KB），分享模块（Canvas 绘制）与图鉴等一次性代码都在首屏包里。

### 2.6 当前技术架构有哪些明显的扩展、性能和稳定性风险？

| 风险 | 位置 | 说明 / 建议 |
|---|---|---|
| 单 chunk 264KB、无分割 | `vite.config.ts` / `dist` | 分享导出、图鉴可懒加载；首屏只保留捕获+战斗 |
| 战斗与 UI 耦合在 `BattleView` 内 | `BattleView.tsx` | 敌方出招若接 AI，需要把"计划 → 意图 → 结算"的边界抽成纯函数，否则规则会被 UI 噪音污染 |
| AI 调用只有分析一个出口 | `shared/ai/client.ts` | 新增战斗决策时需要复用超时/降级/日志/健康检查；不能把 fetch 散进组件 |
| 服务端手写 HTTP + 手写路由 | `server/server.mjs` | 增加 `/api/battle/plan` 时要补 schema、超时、限流、错误处理；两条模型调用应共用同一套 callModel |

| 无错误边界/错误上报 | `App.tsx` | P1 增加 ErrorBoundary + 友好回退 |

| 没有 git 仓库 | 仓库根 | HANDOFF 已说明；P1 改动前建议 `git init` 以便回滚（本次不改仓库管理方式） |
| 测试集中在规则层，UI/接口层无自动化 | `__tests__/` | E2E 只有一条点击路径；P1 需要补 AI 决策协议与降级测试、以及真实 `/api/battle/plan` 冒烟 |
| 无性能埋点 | 全局 | 捕获延迟/战斗调用延迟只能看页脚日志；P1 可把 AI 决策耗时显示在意图条（顺带成为"AI 真的在工作"的证据） |

## 3. 审计后的优先级判断

**不建议做的事**（收益低/风险高）：加账号、排行榜、联机、AI 生图、更多样本素材、纯文字量扩张。

**建议在 P1 做的少数高收益改动**：

1. **敌方 AI 指挥官**：模型在"合法招式白名单"内选招，规则引擎负责结算；意图条标注 `AI 选招 / 规则意图`，失败自动降级。→ 让 AI 真正影响胜负，同时保留可复现与可测试。
2. **一次性战术（3 选 1）**：给被克对局一个真实的翻盘手段，并让"选对手 + 选战术"成为赛前两道决策。→ 修复 0% 被克体验，增加每局差异。
3. **战绩与复现**：每只精灵持久记录 W/L/连胜；结算页显示战绩变化；支持"同种子复现本局"。→ 给第二次游玩一个目标，也让"可复现"从引擎属性变成产品能力。
4. **战斗反馈**：HP 条过渡、回合横幅、击倒印章、最新战报高亮、意图来源徽章、AI 思考中状态。→ 把已有规则"演出来"，成本低、体感收益高。
5. **工程收口**：ErrorBoundary、分享模块懒加载、服务端计划接口的 schema/超时/限流、真实接口冒烟脚本、测试补齐。

以上对应 `docs/P1-PLAN.md`，实施结果与验收数据见 `docs/P1-RESULT.md`。
