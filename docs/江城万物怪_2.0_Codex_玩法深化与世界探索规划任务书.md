### 0.1 已确认的产品决策

1. **P1 Demo 已完成，不能重新从 P0 做起。** 现有拍照/上传、实时多模态识别、出卡、赛前战术、三回合战斗、AI 选招、结算、图鉴、战绩、复现，是可复用基础。
2. **允许大胆扩展核心玩法和世界结构。** 不再拘泥于“两技能、四个敌人、三回合、24 张卡”这些 P0/P1 的阶段性边界。它们可以保留为快玩模式或向后兼容路径，但不应阻止更丰富的完整游戏形态。
3. **游戏的核心不是卡牌生成器，而是“现实物品 → 特征转化 → 可持续角色 → 战术与探索 → 新发现”的完整闭环。** 不能只加图片、名字、卡牌稀有度、数值成长，却仍旧只玩 30 秒。

5. **AI 必须影响可操作体验。** 多模态模型识别物品语义、构造合法能力候选、导演有限事件、操控敌人策略、帮助玩家组合玩法；不能只写卡牌文案和喊话。
6. **设计目标是可玩、好看、愿意重复进入。** 可玩性、反馈、差异化、可收集性、决策深度和创作乐趣优先于后台通用性、微服务拆分、账号体系、排行榜和无意义防御性流程。
7. **全部玩法支柱属于正式规划目标，分批建设，不是任意删除清单。** 可以根据代码和测试证据安排先后顺序，但不能未经论证把成长、探索、队伍协作、机制敌人等全部归入“永远未来”。

### 0.2 “不要防御性实现”要怎么理解

本次要求你积极提出并实现明显改变体验的设计：

- 不要只是微调战术系数、再补一张敌人卡、扩充一批随机名称；要大胆提出**新的游戏循环、新的决策层次、新的地图与目标、真正可变的精灵能力**。
- 不要以“原来三回合封顶”为借口拒绝战术纵深。保留 **Quick Duel（三回合快斗）**，另建 **Expedition Battle（探索/挑战战）**，让队伍、状态、连携、机制 Boss 得以发挥。
- 不要因没有专用生图模型就停止角色个性化。优先将已有程序化插画升级为可组合的角色视觉语言；如有合法、可用的图像生成资源，可作为增强，而不是必需前提。
- 不要因模型延迟就取消有价值的 AI 交互。区分同步关键决策和异步内容生成，通过预生成、预取、缓存、合法动作兜底等方式优化。
- 不要未经观察就否认复杂玩法。以**可玩的纵向切片**验证，再按同一机制扩建内容。
- 不要把产品扩建变成“先重写成企业级架构再做游戏”；优先扩建当前 React/Vite/TS 结构。
- 对未指定的平衡数值、美术模块和战斗设计，Codex 应主动给出可试玩的初始参数、明确假设，并计划基于模拟数据调整，而不是每个细节都回来提问。

**但“不防御性”不意味着**让 LLM 任意设置生命值/胜负、伪装模型调用成功、隐藏照片上传、泄露密钥、允许无限制执行模型生成脚本、让随机生成物品突破数值边界、随意破坏旧存档，或把实测结果改写成宣传文案。

### 1.2 不要把现存限制误认为长期不可变设计

`HANDOFF.md` 将“三回合封顶、第一技能固定 BURST、AI 只能选合法招式、战术赛前固定”等列为 P1 版本不变量。**这些是现有模式的可靠性契约，不等于所有未来玩法必须遵守的永久设计边界。**

Codex 应作如下分离：

- **Quick Duel v1**：继续遵守旧契约；旧存档/回放可继续使用；可以作为一分钟内展示路径。
- **Expedition Battle v2**：采用明确版本号、不同战斗规则、队伍机制、更深的技能槽与状态系统；数值仍只由规则引擎结算。
- **共享不变量**：用户数据保护、AI 行为可核查、输入 schema、战斗可复现、非负有限数值、超时降级、参数白名单。

迁移前必须检查已有测试如何写死 `MAX_ROUNDS`，不能“随手改成 8”导致所有旧回放与数值假设失效。

### 1.3 现阶段最重要的产品缺口

1. **拍照后的产物与原物体关系还不够深**：从热干面、雨伞、轮渡中生成的角色虽不同，但差异未形成足够丰富的战术机制。
2. **没有长期动力**：图鉴虽有 W-L、连胜，玩家缺少探索、培养、搭配、任务和大型目标。
3. **战斗选择太少**：每只两技能、固定三回合、四个数值型对手，AI 的策略空间受限。
4. **武汉特色主要是主题皮肤**：需要把地标/文化/天气/场景转化为有差异的区域规则与故事。
5. **表现层尚欠“召唤/发现”瞬间的记忆点**：程序化小怪、美术卡面虽已成体系，仍有升级为更强演出和个性化形体的空间。

## 2. 产品定位与不应该走的歧路

### 2.1 一句话定位

**拍下身边的物品，召唤属于自己的江城怪物，带着它们在一个原创的武汉幻想世界里探索、组队、培养、挑战、收集。**

玩家创造的是自己的队伍和故事，而不是仅获得一张 AI 生成图片。

### 2.2 三个必须始终成立的欲望

| 欲望 | 体验实现 | 可以验证的行为 |
|---|---|---|
| **创造欲** | “这个杯子/雨伞/手工作品会变成什么？”；不同形态和语义产生不同能力 | 用户主动找新的现实物品拍摄 |
| **收集欲** | 区域图鉴、发现链、稀有组合、分支进化、挑战收藏 | 用户为目标探索或补全图鉴 |
| **策略欲** | 三人队伍、属性/机制搭配、首领规则、队伍连携 | 用户输后主动改阵容而不是只等刷出高攻击 |

附加：城市情感、故事体验、可分享的原创小怪、单人即可畅玩。不要将“社交+排行榜”当作必需复玩理由。

### 2.3 强制设计原则

- 捕获门槛低：首只怪不要求注册、不要求出门、不要求定位、不要求先读百科。
- 物品特征是规则输入，不是装饰文本；用户能看到“为什么它获得了这个能力”。
- 不让更贵、更稀有的现实物品天然战力更高；保证日常物品也能创造好用角色。
- AI 负责构思、解释、编排，代码负责合法能力选择与数值；视觉上的自由不能造成不可控的数值膨胀。
- 武汉本地化不应排斥其他城市用户：可从任何地方捕获，武汉主题以首个世界赛季为主。
- 首次 30 秒内应看到有生命感的角色；首场小战 ≤1 分钟；深度玩法按需渐进解锁。
- 不以真人 GPS 打卡作为参与门槛，不鼓励进入危险或受限制地点拍摄；线上虚构地图与图片输入即可探索。
- 角色、世界、美术和术语应是原创设计，避免直接复用知名怪物收集 IP 的名字、精灵设计与标志性布局。

## 3. 新的三层核心循环

### 3.1 微循环：20—60 秒，“捕获—惊喜—马上试用”

1. 玩家拍/传一个现实物体（或点样例）。
2. 预处理与视觉理解抽取：类别、主体、可见形状、纹理、材料线索、功能线索、颜色与文化主题；严格标注哪些特征可靠、哪些只是推测。
3. 映射系统从稳定的**特征标签与构筑词缀**生成技能/被动/外形组件；AI 补齐个性名字、口吻和故事，返回受限结构化意图。
4. 屏幕上经历有辨识度的召唤演出。用户可以选择一种特性路线（例如“守护”“机动”“诡计”），获得立刻能使用的精灵。
5. 一键进行教学快斗或加入队伍，看到该能力在游戏里如何产生效果。

**惊喜不是随机给一个稀有度，而是“我拍的是伞，它真的会开盾挡攻击；我拍的是轮渡，它可以搭载队友穿越江面障碍”。**

### 3.2 中循环：5—12 分钟，“探索—组队—事件—战斗—解锁”

- 选择一个区域探索关卡，遭遇环境效果、敌人队伍和随机但有规则的事件。
- 在岔路做选择：补给、风险挑战、特殊捕获材料、支线任务、首领情报。
- 使用 2—3 只怪物组成战队，利用主动换位、支援和连携应对不同敌人。
- 获得材料、经验、关系/羁绊、发现记录和新的路线。
- 关卡结束能看见城市场景变化与可解锁的下一节点。

### 3.3 长循环：30—90 分钟累积，“区域图鉴—进化—区域挑战—世界推进”

- 从武汉主题的多个区域推进故事。
- 按目标收集特定特征、属性和能力组合，养成几只具有特色的核心成员。
- 挑战各区域独特的机制 Boss；获得支撑新路线的关键物品。
- 分支进化或合成获得独特的外观与战术特性。
- 完成江城篇主线后，仍可以自由捕获、挑战周目变体、创作分享与补全图鉴。

**验收要点**：玩家每个中循环都应至少得到一次新变化（阵容解锁、技能选择、可见区域变化、剧情事件或图鉴发现），而不是重复打相同的四个敌人。

## 4. 六大玩法支柱：全部纳入目标

### 4.1 现实捕获与语义造物系统【核心】

**目标**：让现实世界变成可复用的“角色素材库”，每次捕获的差异可解释又可预测。

#### 数据流程

`照片 → 局部提取/视觉摘要 → 受约束物体标签 → 物体特征组合 → 种族底盘/外形配件/能力模组 → 战力预算校验 → 可保存怪物`

推荐标签维度（必须为可编辑枚举，不允许 LLM 发明无限标签）：

- `category`：food / tool / nature / vehicle / building / stationery / textile / toy / other。
- `shape`：round / long / flat / foldable / layered / branched / hollow。
- `texture`：smooth / rough / woven / soft / rigid / liquid_like。
- `function`：protect / carry / connect / bind / illuminate / nourish / propel / decorate。
- `theme`：river / rain / flower / street_food / bridge / campus / invention / generic。
- `evidence`：来自可见图像的特征、来自用户确认的功能、推断但不确定的特征，三者分别标记。

物品标签影响能力的方向样例：

| 原物品 | 可见/可确认特征 | 游戏机制 | 不是哪一种简单映射 |
|---|---|---|---|
| 雨伞 | 可折叠、遮挡、圆弧伞面 | `开伞屏障`、天气减伤、保护队友 | 不是简单“工具属性 +10 防御” |
| 热干面 | 食物、细长/缠绕、芝麻主题 | `缠线牵制`、一回合粘连、回复/补给主题 | 不因为是食物就永远只有回血 |
| 轮渡/船形物 | 载具、承载、跨越水面 | `渡航换位`、把队友移到安全位、江流环境协同 | 不直接让真实位置成为隐私输入 |
| 樱花 | 花瓣、轻盈、飘落 | `落樱标记`、闪避/延迟触发 | 不只生成粉红色图片 |
| 水杯 | 容器、盛水、易碎/坚固可确认 | `储流蓄能`、释放积攒的资源、元素调配 | 不任意宣称杯子是金属或玻璃 |
| 笔记本 | 纸页、记录、层叠 | `留痕复写`、复制一次队友的支援效果 | 让普通文具也有独特用途 |

应提供“为什么这样生成”的可见卡片：`照片中的伞面 → 遮挡标签 → 守护型被动`。用户可以对识别错误的类别或功能进行一次确认/更正，并重新生成合法分支。

#### 反单调机制

- 相同物品不同构图，不应无缘无故导致巨大战力波动。
- 同类物体也允许不同 build：固定“本源特性” + 一个可选“成长方向” + 小范围可控词缀。
- 属性不是唯一差异来源；**被动、环境适应、队伍定位与技能组合**更重要。
- 任何随机稀有度若存在，只能影响美术、收藏与横向差异；禁止直接决定胜负强弱。

**验收**：至少 12 类高频现实物品跨 4 种机制职责产生明显玩法差异；同图相同生成配方/种子可复现；人为改正标签后能看见能力机制变化。

### 4.2 多精灵队伍与策略战斗【核心】

不再只有“单卡两技能三回合”。正式规划包含三条模式：

1. **Quick Duel**：继承现有三回合快斗，适合首分钟演示、移动端碎片时间和旧战绩兼容。
2. **Expedition Battle**：主线标准战；推荐三人小队、单名主动上场、两位支援、5—7 个决策轮次或达到明确胜负条件；允许中途切换、能量/冷却/状态机制。
3. **Boss Trial**：首领拥有可读的阶段机制/意图，不是单纯 3000 HP；玩家可以用不同策略破解。

**推荐 2.0 资源与机制草案（由 Codex 平衡论证后确定）**：

- 队伍：3 只；1 主战、2 支援；每只可配置 3 个主动技能中的 2 个 + 1 被动（与 v1 两技能兼容）。
- 全队公共“灵感/共鸣”资源：攻击、守护、环境触发可累积；换位/连携消耗；限制无限滚雪球。
- 互动：属性克制、状态（潮湿/缠绕/脆弱/护盾/蓄力）、天气/地形、主动换位、连携。
- 回合提示：AI 预测意图或展示可读威胁，让玩家能用防御、转换/支援采取有意义的决策。
- 快斗不必拥有所有机制，深度战才需要队伍与组合。

**至少定义 8 种有名字、有独特应对的敌人原型**：护盾型、反弹型、持续伤害型、召唤型、资源压制型、变身型、控制型、快攻型。每种应具有“可观察的预兆 → 玩家可采取的反制 → 数值可复现”的机制链。

首领参考：

- **风雨电台（雨季区域）**：每两轮宣告一次暴雨，无遮蔽单位受额外影响；雨伞型精灵不一定最强，但其遮挡能为队友争取一次安全行动。
- **桥影守卫（桥梁区域）**：轮流封锁前/后排通道，鼓励换位和携带“连接”特性的精灵。
- **早味大厨（早味区域）**：不断积累“热度”，玩家需要打断、冻结或在对的时机集中爆发。
- **樱信档案员（校园区域）**：记录玩家重复使用的技能并产生针对性抵抗，鼓励更换打法。

**重要**：Boss 的强度不能完全建立在模型临时发明规则上。机制定于数据表/规则 DSL，AI 只在合法行动中决定策略和播报。

### 4.3 捕获后的成长、羁绊与分支进化【核心】

玩家要愿意养自己的那只“来自日常生活的怪”。

建议成长从**横向解锁与角色风格**切入，而不是堆等级与线性数值：

- 经验来自探索、战斗和特定任务，等级只提供温和能力上限，避免刷级碾压。
- 熟练度：同一精灵在防守/支援/输出方向上参与不同战斗，解锁可选择的特性或技能侧向变化。
- 羁绊：特定精灵一起行动触发协作（例如遮挡 + 渡航、缠绕 + 潮气），必须满足可解释的标签条件。
- 分支进化：达到成长条件后，给玩家**至少两条可预览路线**，例如雨伞从“守护伞灵”或“疾风滑翔者”中择一；更换的是玩法定位与外观，不只是稀有度数字。
- 进化历史可追溯：原始物品标签、选择的路线、解锁方式、当前形态、版本；保留原卡的故事。
- 合成/共鸣：把两个物品特征组合成新机制，但**不销毁玩家不可恢复的心爱精灵**作为默认规则。先考虑配方合奏、技能传承或临时联合形态，而非消耗本体。

设计要求：**至少有一条进化路径能改变战术角色**，例如原本守护型伞灵进化成控制型疾风角色。不能只把立绘变复杂。

### 4.4 武汉主题开放地图与区域探索【核心】

不是做真实 GPS 地图，也不是完全开放 3D 世界。推荐**具有丰富交互节点的原创二维江城幻想地图**；名称可借鉴城市气质，场景与故事必须明确虚构。

五个区域建议：

| 区域（暂定名） | 主题与视觉 | 独特玩法 | 特色掉落/收集 |
|---|---|---|---|
| 过早巷 | 热干面、豆皮、清晨市井的幻想混合 | 热度/补给/节奏连招；街区声望 | 早味配方、食物系变体 |
| 江风渡口 | 江面、轮渡、雾、潮汐 | 船队换位、渡口选择、环境潮气 | 江流系材料、渡航图鉴 |
| 桥影工坊 | 桥梁、机械、城市交通 | 连接/断路谜题、护甲与装置 | 机巧模组、桥影首领 |
| 樱语山坡 | 校园树影、樱花与老建筑意象 | 隐藏路线、记忆线索、协作任务 | 花叶系材料、校园故事 |
| 雷鸣创想站 | 校园科技展、创意物件、实验装置 | 装置组合、挑战规则变化 | 科创模组、最终挑战 |

（若最终采用真实武汉地名/照片，Codex 应核实地名、素材授权和事实描述；无法核实时使用明确的虚构地名。）

**最小地图循环**：区域选择 → 3—5 个岔路节点 → 一次随机/因果事件 → 一场机制战或可选事件 → Boss/宝箱 → 地区进度与图鉴变化。

事件不只是文本 + 一次资源增减。例如：

- 在江风渡口，玩家选择帮助维修一艘虚构渡船，临时损失材料，但下一关获得一个运输支援位。
- 在过早巷，为一只热干面精灵解决“缠线失控”，解锁一个新的牵制技能分支。
- 在樱语山坡，以特定能力连接两处树影，发现一段角色记忆与隐藏配方。
- 在桥影工坊，单靠输出无法通过，必须重构队伍的连接能力。

应设计“首访奖励、路线分支、可回访内容、区域 Boss、成就/图鉴”五层动机，让地区不只是一张背景图。

### 4.5 可组合任务、收藏与创造系统【核心】

至少支持四类任务：

1. **物品发现任务**：如“捕获一种能遮挡的物体”或“一件与城市雨季有关的物品”；可以使用手机图片或内置素材完成，不要求现场地理位置。
2. **队伍构筑任务**：例如“用一个守护者和一个江流伙伴完成挑战”；促进不同物品的组合。
3. **区域事件任务**：通过选择和战斗改变某一区域状态，而不是单纯收集五个材料。
4. **高阶挑战任务**：限定技能/阵容/天气条件，打败机制 Boss，支持复现与分享。

**图鉴不是无限卡片列表**，应支持：收藏锁定、按物品类/元素/特征/能力过滤、成长分支展示、区域来源、历史战绩、已发现/未发现的机制配方。

建议可分享两种原创作品：

- **角色档案卡**：现在已支持 PNG；升级后包含物品特征来源、进化路线、代表性战绩，不公开原始照片或位置。
- **战术挑战码 / 种子**：分享合法的场景配置、队伍模板或战斗 seed（注意不要暴露用户图片、私有文本或 API 密钥），让朋友复刻挑战。

不强制引入账号、好友、聊天、社区审核才能完成离线单人核心体验。

### 4.6 AI 主动导演与有性格的对手【核心】

当前 AI 已能选择敌方出招。2.0 不应只是再增加 8 个可选技能，而应让 AI 对手有不同的行为策略：

- **领地守卫**：保护核心装置，倾向防守、拖延和惩罚贸然攻击。
- **搜集家**：优先抢夺场地资源，通过技能和环境争取优势。
- **机巧赌徒**：使用可预告的高风险连招，玩家可打断。
- **临场学习者**：根据玩家最近数回合策略调整，但只能读取当前战斗允许的历史信息。

导演系统可以根据玩家队伍特征选择合法支线、鼓励不同构筑尝试、生成有上下文的敌方台词；**AI 不允许生成与规则无关、无法解释的惩罚或奖励**。

NPC 对话不应成为主要玩法。让它们的行为转化为可玩的任务、环境变化、交易方案或战斗意图。

## 5. 关卡叙事和长期世界目标

### 5.1 建议世界观：万物回响，江城醒来

在一个与现实武汉有文化联系、但完全虚构的平行城市中，日常用品会因“回响”化为小怪物。玩家成为一名“记录员/造物者”，收集失散的回响，逐步修复五个区域的失衡。

关键主题：**熟悉的现实物品在游戏里展现意想不到的另一面**。故事要轻盈、奇妙、有幽默感，不写成严肃城市宣传片。

### 5.2 三幕主线，五个区域可部分自由选择

- **第一幕：第一只回响**（过早巷、江风渡口）：捕获首只精灵、组建两人队、认识第一位有特色的 AI 对手；开放第二条区域线。
- **第二幕：桥上的异变**（桥影工坊、樱语山坡）：环境机制、队伍组合、分支进化首次成为必要策略；引出核心异常。
- **第三幕：造物夜**（雷鸣创想站）：玩家以不同地区获得的能力解决最终挑战，允许多种构筑取胜；结尾生成可回放的“我的江城图鉴/故事”。

建议主线总时长先以 45—90 分钟分段累计为设计目标，玩家随时中断能接续；具体节奏以试玩数据决定。**不必一次坐在网页前玩满 90 分钟。**

### 5.3 三个让故事有“玩家专属感”的机制

1. 玩家第一只捕获精灵成为故事中的伙伴，后续剧情与任务会引用它的真实能力，而不是只把名字插入模板。
2. 每区域至少一个可改变后续区域的选择，如先帮渡口还是先修工坊，造成不同支援方式。
3. 年度/章节结束时的故事报告引用玩家实际捕获、队伍、打败的首领与重要分支，不虚构从未发生的事件。

## 6. 核心战斗系统的具体设计任务

### 6.1 战斗从“数值比较”升级为“信息—对策—连携”

玩家每回合至少有两种**真正不同**的有效选择：

- 追求输出：迅速结束战斗，但可能承受下一轮关键机制。
- 保护/换位：延后伤害，积累资源、打断敌人或保护关键伙伴。
- 控制/反击：响应 Boss 的预告，改变战斗规则中的局面。
- 支援/连携：利用前期收集的不同物品特征形成特殊打法。

不要让所有最优策略都退化为“带最高攻击的怪，三个回合连续 BURST”。

### 6.2 明确新版本的数值与行动预算

Codex 在规划里必须提出可模拟的方案，至少定义：

- 单位属性：生命、攻击、防御、速度是否继承以及成长范围。
- 每只精灵技能槽与被动槽数；技能类别、使用次数/冷却、能量成本。
- 队伍换位行动成本、换位后是否可攻击、支援效果如何结算。
- 状态增减、持续时间、叠加上限、驱散方法与伤害上限。
- 环境事件与天气效果的发生时机。
- Boss 阶段变更与安全的预告方式。
- 胜负判定、平局及超时裁定；不得无限回合僵局。
- 每次战斗如何保存实际 AI 计划以复现，而非只保存 seed。

旧版回放依赖 `seed + tactic + plans + player moves`；2.0 进一步需要规则版本、初始阵容快照、技能定义版本和全部合法事件序列。

### 6.3 样例战斗：江风渡口的暴雨守卫

玩家队伍：热干面（缠绕控制）、雨伞（守护）、轮渡（机动）。

- **前一回合**：Boss 预告下一轮“大雨压境”；玩家可以提前蓄力输出，也可以切换到雨伞铺开护盾。
- **当前回合**：若护盾到位，雨水转为“蓄潮”资源；若没有护盾，队伍受到持续潮湿/行动压力（由确定性规则定义）。
- **后续回合**：轮渡可消耗蓄潮资源发动“渡航换位”，把主战精灵拉离危险位置；热干面利用缠绕打断 Boss 的下一轮引导。

不同构筑可以用控制、快攻或持续防守通过，但要求玩家理解机制而不是赌随机。

### 6.4 机制 Boss 的 AI 价值

AI 决定在**合法动作集合**中何时防守、何时追击、何时针对玩家常用策略；Boss 的预告、状态计算、伤害和阶段转移由代码执行。若模型响应延迟，可在战斗进入时异步计算前几个关键节点，或只在关键战术回合使用模型，其余交由规则 AI；界面诚实显示来源。

## 7. 捕获生成系统：从“AI 给设定”到“可玩的物品语义编译器”

### 7.1 应有两个层次

- **确定性能力模板**：固定的特征库与效果组合，既支持 AI，也支持离线。
- **AI 创作层**：视觉理解、主题命名、特征解释、技能路线推荐、原创故事与环境互动构思。

模型输出为 `CreatureIntent`，包含可信度、证据片段、标签建议、玩法职责建议、外观配件建议；**最终属性、技能、被动、成长潜力由规则编译器合法化**。

### 7.2 示例 JSON 契约（仅供 Codex 细化）

```json
{
  "objectCategory": "tool",
  "observed": ["foldable", "curved_surface", "rain_related"],
  "inferred": [{"tag": "protect", "confidence": 0.84}],
  "playerConfirmed": [],
  "theme": "rain",
  "roleHint": "guardian",
  "passiveHint": "canopy_shield",
  "appearance": {"body": "fan", "pattern": "rain_lines", "accent": "hook_handle"},
  "name": "伞跃跃",
  "flavor": "下雨的时候最爱逞强。"
}
```

所有外部字符串必须限制长度；所有标签/能力提示必须白名单化；未匹配标签退回合法默认路线。这个协议不等于允许模型输出 `stats:{attack:99999}`。

### 7.3 特征冲突与用户参与

“杯子究竟是陶瓷还是玻璃”“图里是一张照片还是屏幕截图”等不能靠低置信度猜测硬决定。给用户一个快速的“是/不是/我自己选”入口；允许玩家选一个合法风格分支。**纠错本身也可以是轻量小游戏的一部分**，让用户觉得自己在塑造角色，而不是被动等卡。

### 7.4 不依赖 AI 生图也能做出丰富视觉

目前 `MonsterSprite.tsx` 使用程序化双色套印插画（交接记录：6 体块 × 6 纹样 × 5 配件）。Codex 应提出扩容到组合式外观系统：主体轮廓、材质笔触、五官/表情、道具、动态部件、元素效果、进化附加层等。应支持同一角色进化后明显变化，但仍可认出原始物品。

不要轻易抛弃现有孔版双色印刷 + 方格观测本视觉语言。可以让五个区域有不同的第二强调色或背景纹理，保持整体识别度。

如果可接入合法且可负担的生图模型，可将其作为可选立绘增强，必须保证无生图时玩法完整、生成失败不丢卡、视觉资产来源可追溯。

## 8. 武汉特色不是主题海报：区域规则与内容实例

### 8.1 设计基调

- 有武汉识别度，但不是城市宣传册，不堆砌地标知识点。
- 有城市日常的幽默感，例如“早味精灵争论豆皮和热干面谁该当主力”；但不侮辱真实群体，不制造地域刻板印象。
- 可参考武汉江河、桥梁、渡口、老街、小吃、校园、樱花等公共文化意象；具体历史事实和非公开校园空间信息需核实。
- 游戏核心不依赖用户当前定位，可以上传武汉旅行照片，也可以上传宿舍里的普通物品。

### 8.2 区域互动样例

| 关卡 | 交互玩法 | 可复玩变化 |
|---|---|---|
| 过早巷外卖危机 | 在有限回合内用物品技能协调补给、阻断“热度失控”的 Boss | 不同队伍可用补给、控制或爆发 |
| 渡口浓雾 | 在地图岔路选择航线，利用承载/照明/侦测标签找捷径 | 同 seed 可换路线；改变支线奖励 |
| 桥影机关 | 玩家用连接/保护/机动类型能力操纵机关 | 找隐藏路线需要改变队伍组合 |
| 樱坡守望 | 与 AI 角色解开小任务，选择帮助哪只精灵 | NPC 信任与后续事件分支 |
| 创想之夜 | 利用几件真实物品的能力完成最终组合挑战 | 多种合法构筑可通关 |

### 8.3 武大限定主题作为可选赛季

在主世界之外，可设计“珞珈校园季”：樱花、社团招新、实验室小物件、图书馆文具、校园活动等主题的限时关卡或收藏。**用户不必在校内、无需上传学生证即可玩**。以虚构的校园场景叙事，不虚构官方授权。

## 9. 长期成长与图鉴：不要做成数值刷刷乐

### 9.1 成长反馈

- 每完成一次探索，明确告诉玩家“新获得了什么”：一个新区域、一次技能选择、一段角色故事、一种配方、一个新的队伍可能性。
- 设定角色个人小目标，如“伞跃跃挡住三次大伤害后开放护卫分支”；不是必须刷 100 次经验。
- 允许低成本重置技能方向，避免首次选择后永久锁死心爱角色。
- 让旧角色有价值：任务/挑战可能需要特定特征能力，而非战力最高的一张卡。

### 9.2 图鉴与收集

建议包含三层图鉴：

1. **个人造物图鉴**：用户拍出来的精灵与来源标签，支持锁定、归档、筛选和版本迁移。
2. **江城区域图鉴**：区域里的原生 NPC/敌人与已发现故事，不是要求用户拍某个真实地点。
3. **能力发现图鉴**：玩家已见过的特征组合、连携、进化分支和机制知识。

“未发现”的提示要能激发捕获欲，例如“缺一个能照明的伙伴”，而不是展示 999 个问号。

### 9.3 资源经济

推荐控制为三种主要资源以内：探索补给、成长材料、区域信物。禁止几十种互不相干货币。付费货币、广告与签到不是本次版本目标。所有获取与消耗有明确经济流向，防止无限刷取导致失衡。

## 10. AI 角色与 Agent 工作流的进一步深化

### 10.1 四种受约束的模型任务

| AI 任务 | 输入 | 可输出 | 不得输出 |
|---|---|---|---|
| `analyze_object` | 图片压缩数据、合法标签库 | 可见特征、类别、名称建议、技能角色意图 | 任意最终数值、敏感推断、上传位置 |
| `battle_director` | 当前合法战场快照、候选动作 | 选招、原因、战术意图、播报 | 非法技能、伤害计算、改胜负 |
| `quest_director` | 地区进度、队伍能力、已发生事件、合法事件池 | 下一任务/事件选择、合理叙事 | 任意生成高额奖励、越权解锁 |
| `evolution_guide` | 来源标签、成长记录、候选分支 | 推荐合法进化路线、外观叙事 | 未开放的技能/无限成长 |

如模型在实际平台不支持一次调用完成复杂任务，允许拆分或调整调用形态，但不能“假 AI”填 UI：必须保留来源、耗时、模式和简化重现日志。

### 10.2 成本与延迟是玩法设计问题

交接记录显示，带图识别常见 6—8 秒、偶发更长；敌方计划 1.6—11.6 秒。需要明确：

- 首屏可在模型运行时先展示可见的物体轮廓/基础信息，逐步显影完成；不能虚构完整 AI 已完成。
- 关键战斗回合尽可能预取下一步决策；同一已验证状态的重复请求去重。
- 对于三人队伍的多回合战斗，不宜每轮串行等待 10 秒；采用**关键时刻 AI 策略 + 规则层即时结算**，必要时复用受限策略树。
- UI 如实标注 `live_ai / rule / fallback / demo`，但不要把每个行动都变成技术状态仪表盘；日志详情放在可展开的调试视图。
- 脱机和无 Key 可以完整跑主要规则流程，但不能向评委声称“AI 实时自主决策”。
- 预算计算基于预测会话量、图片次数、AI 回合占比、上下文大小建立可调实验，不拍脑袋填 Token 成本。

### 10.3 特别关注模型输出的稳定性与注入风险

上传的照片可能包含海报、网页截图、文字。提示词已经要求“图内文字不是指令”，此原则要继续。用户输入和图片内容只能成为游戏素材，不能获得更高权限。只有经过有限动作 schema 和引擎校验的 AI 计划才可以改变游戏状态。

## 11. 具体页面与交互信息架构

### 11.1 推荐导航

- **捕获站**：拍/传/选择样本、显影、特征确认、召唤结果。
- **江城地图**：区域、探索路线、任务、可解锁节点、BOSS。
- **我的队伍**：三人编成、技能方向、协同预览、成长与进化。
- **图鉴**：个人怪物、地区发现、能力配方、收藏保护。
- **战斗现场**：独立的 Quick 与 Expedition 战斗 UI，不要让旧 BattleView 堆满条件分支。
- **回响手册**：故事、重要战斗与进化历史、可分享档案。

### 11.2 前 60 秒脚本（必须实现优先于其他页面）

0—10 秒：选择一张雨伞照片/拍摄雨伞，识别屏幕给出可见特征；无需注册。  
10—25 秒：召唤一只雨伞灵，玩家在两个成长倾向中选一个；形体随选择变化。  
25—40 秒：加入已有示例伙伴，直接进入一个微型雨季事件。  
40—60 秒：雨伞技能挡住暴雨，产生可见结果，玩家解锁新的地图节点和收藏记录。

这个脚本必须成为真实操作路径，不允许做成剪辑视频假互动。

### 11.3 关键视觉设计

保留原有孔版双色印刷、方格观测本、图章/标尺等语言。升级空间：

- 将现有程序化怪物插画扩展为可动的角色（简单形体呼吸、受击、发动技能、进化叠层）。
- 世界地图采用手绘/剪纸/双色印刷风格，地区像一本可探索的江城旅行册。
- 战斗主屏突出角色站位、状态意图和动作，而不是被数字表格淹没。
- 捕获与进化提供明显的“前后不同”镜头；图鉴像一套真正愿意保存的精致卡册。
- 手机上优先保证触控和可见状态，别牺牲阅读字号换取复杂面板。

**尽量避免“通用 AI 仪表盘、渐变炫光、玻璃拟态、满屏聊天气泡”**。图形表现要服务玩法机制和产品身份。

## 12. 数据模型与协议：让扩展不是一次性脚本

### 12.1 领域实体（供 Codex 结合代码落实）

- `MonsterV2`：保留旧 `Monster` 的稳定身份与来源标签，增加可选特征、被动、角色定位、成长路线、形态版本。
- `CaptureEvidence`：可见特征/推断/用户确认三类证据，不应存原始照片；字段可按最小必要保存。
- `Party`：怪物引用、位置、主动/支援角色、技能配置。
- `BattleRuleset`：`quick_v1 | expedition_v2 | boss_v2` 等显式版本，禁止拿全局 `MAX_ROUNDS` 强行兼容。
- `BattleEvent`：所有行动和环境状态转移；按版本可重放。
- `WorldProgress`：区域解锁、任务、分支选择、节点状态。
- `QuestInstance`：任务定义 ID、目标、进度、奖励、合法触发事件、完成状态。
- `EvolutionRecord`：来源、条件、选择、前后版本、可回放的外观与能力变化。
- `CollectionIndex`：收藏锁定、图鉴发现、技能配方解锁；存档需做迁移。

- 同一初始快照 + 同一动作序列 + 同一规则版本 + 同一 AI 计划序列，结果一致。

- 用户能在结算看见“关键行动”与对应前后数值，避免只显示总伤害。

### 14.3 设计表现策略

优先先把角色表现做活，再去做大量静态背景。不要为了制作 5 张昂贵的大地图插画拖延最核心的“召唤和战斗”体验。角色视觉方案可以结合 SVG 动画、Canvas 或轻量 PixiJS，但必须评估与现有代码集成成本。

## 18. 三个演示剧本：证明玩法已改变

### 18.1 90 秒版：一把雨伞的逆袭

0—15 秒：上传雨伞或点击示例，AI 得到“遮挡/折叠”特征，界面标记可见证据。  
15—30 秒：伞跃跃从造物台召唤出来；选择守护分支，出现明显的视觉变化和新能力。  
30—45 秒：组成三人队伍，进入江风渡口。  
45—70 秒：Boss 预告暴雨；雨伞开启屏障，轮渡触发换位，热干面成功牵制；伤害/状态清晰反馈。  
70—90 秒：解锁渡口支线和进化材料，图鉴记下“伞跃跃首次救场”。  

**核心演示证据**：现实物品语义→合法能力→真实战斗结果→长期进度变化，是同一条真实链路。

### 18.2 三分钟版：两种物品，两套打法

先演示雨伞守护流，再演示热干面缠绕控制流。选择同一挑战，以相近战力但不同队伍过关，展示玩法不仅靠更大的攻击数字。最后打开江城地图和进化预览，证明不同物品引出不同的长期路线。

### 18.3 10 分钟体验版：个人江城冒险

完整经历捕获→选择特征→组队→路线选择→两场不同机制战→获得材料→进化分支→图鉴→分享卡/挑战码。玩家应能不看说明自己走通主要流程。

## 19. 验收：什么叫“做出 2.0”，而不只是新界面

### 19.1 功能硬验收

- 保留现有 P1 捕获/战斗/分享/图鉴可用链路；旧卡迁移，不静默丢失。
- 拍物体可生成带真实、可解释特征来源的角色；不同高频物品映射出不同**机制职责**。
- 至少有一条三人队伍 + 连携 + 机制 Boss 的完整可玩链路。
- 至少两个区域形成探索任务、奖励、成长、再挑战的闭环。
- 存档/刷新/复现按规则版本工作；AI 失败不致使整局丢失。
- 玩家可以选择不同发展方向；同一只伙伴进化分支至少有一种能改变其打法。
- 武汉主题真正映射到关卡和环境机制；不需要 GPS 或物理到访。
- AI 真实参与的环节可核验，不得把本地规则冒充实时模型。

### 19.2 游戏性验收（建议实测门槛，非已达成绩）

找至少 5 位未参与开发的学生；观察而不是只给问卷：

1. 是否能在 60 秒内从物品变怪物并看到其能力；
2. 是否主动改变队伍、路线或进化分支以应对失败；
3. 是否有玩家因为想获得某个能力而主动寻找第二件现实物品；
4. 是否愿意探索第二个区域，而不是完成首场战斗就退出；
5. 是否能说清楚自己的一只怪为什么独特；
6. 是否出现明显的卡关、等待、界面理解问题；
7. 是否有可复现的失衡套路（例如固定一队能碾压所有 Boss）。

原则上，至少应观察到多名试玩者**主动再拍/再组队/再探索**其中一种行为；若没有，优先修核心机制，不要仅扩美术或任务文本。

### 19.3 测试与指标

- 原有 37 条单测需保留等价覆盖；扩充 P2/P3 关键规则、迁移、任务、Boss、AI 降级、E2E；不机械追求测试数量。
- 对同一规则版本 + 种子 + 事件日志重放结果做确定性断言。
- 至少模拟 1000 局跨构筑对战，报告极端胜率、无限循环、无意义技能、持续状态异常。
- 记录首只出卡耗时 P50/P95、首场实战耗时、每局 AI 调用次数、AI 降级率、移动端异常。
- 保证用户上传原始照片不被默认持久化，若后续想开放自愿照片收藏则必须另做明确授权流程。
